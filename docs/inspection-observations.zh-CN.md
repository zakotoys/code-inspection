# 检查变化与结果有效性

## 本次改动解决什么问题

1. 保存启动检查后，不再等待整个检查结束才处理后续编辑、删除通知。
2. 正在运行的任务只有覆盖新请求的全部范围，才能直接复用。否则取消旧任务，并以两个请求的合并范围重新检查，避免漏掉新文件。
3. 不再根据“保存后 1500 毫秒以内”或“50 毫秒内重复事件”判断是否忽略文件变化。保存时记录文件内容哈希，后续通知只有内容相同才作为保存回声忽略。读取失败时保守失效。
4. 增加有效检查结果之间的基线比较，不把第一次看到的存量问题当成新增。
5. 统一诊断标准化和去重，运行编号、失效代数和返回顺序不再改变相同诊断的 ID。

## 从检查到变化的过程

```text
编辑器 / CLI / MCP 请求检查
→ 服务确定检查器、项目和文件范围
→ 执行检查
→ 检查是否完成、是否已失效、文件是否仍有未保存修改
→ 更新当前结果
→ 完整结果与对应范围的上次有效基线比较
→ get_run 返回 changes
```

`changes` 包含：

| 字段 | 含义 |
| --- | --- |
| `baseline` | 本次覆盖的结果分组此前都没有基线；不是“当前代码没有错误” |
| `initializedFiles` | 本次首次建立观测基线的文件 URI |
| `added` | 相比上次可比较结果，新增的诊断记录 |
| `resolved` | 相比上次可比较结果，不再出现的诊断记录 |

第一次检查得到 A、B：建立基线，新增和消失都为空。下一次得到 B、C：新增 C，消失 A。

检查器、项目和范围类型分别维护基线。只检查 a.js 时，不会把 b.js 的问题记成消失。第一次检查一个没有错误的文件也会建立基线。扩大检查范围时，之前没有观察过的文件先建立基线，不把其存量问题记成新增；因此一次结果可以同时包含老文件的差集和新文件的初始化。

## 哪些结果不能推进基线

- 工具执行失败、取消或被新任务替代。
- 结果返回时相关文件仍有未保存编辑，或检查代数已经失效。
- 结果超过 `maxFindings` 被截断，`summary.truncated` 为 true。

以上情况不产生 `changes`，不能把缺少该字段解释为“全部修好”。失败或不完整结果不会抹掉以前的有效基线。配置变化后重新建立基线；删除文件清理相应基线数据，不把删除报告为修复。

## 明确边界

- 比较的是诊断字段，不是智能识别真实缺陷。错误移动行号，仍可能表现为旧记录消失、新记录出现。
- 严重程度、规则、来源、完整位置或消息不同的诊断不会被误合并。
- `changes` 是按运行保留的独立比较结果，但不是第三阶段的游标历史服务，也不持久化到磁盘。服务重启会丢失基线，运行记录淘汰会丢失相应比较结果。
- `get_run.findings` 仍然读取当前结果集合，不能当作旧运行的完整历史照片；新增的 `changes` 才是该运行保存的比较结果。
- 同一个变化被多次读取，不代表应该重复提醒。执行提醒前仍需复核当前结果。
- 内容哈希现在同步读取保存文件；很大的源码文件可能延迟事件处理。缓存只保留最多 1000 个哈希，不保存文件正文。文件系统通知也不是逐次写入的完整审计日志。
- 磁盘外部修改使旧结果失效，不会自动安排新检查。
- 未新增暂停/恢复、持久化、分页版本或设备反馈功能。

IPC 协议版本升为 3。切换版本后应重启旧服务和客户端，不提供旧协议兼容层。

## 验证与代码入口

- `packages/core/src/findings.ts`：诊断比较字段、稳定 ID 和去重。
- `packages/runtime/src/finding-baselines.ts`：按范围管理基线和差集。
- `packages/runtime/src/service.ts`：任务范围、结果有效性、保存内容协调和变化记录。
- `packages/runtime/src/lsp.ts`：文档事件与检查完成等待分离。
- `packages/runtime/src/mcp.ts`：`get_run` 的变化输出结构。

运行 `npm run check` 验证编译与测试。新增回归覆盖真实 LSP 子进程中“检查尚未结束就继续输入/删除”、检查范围扩大、保存后外部修改、失败与截断结果不推进基线，以及 MCP 返回结构。测试不等于已完成真实用户编辑器体验、Linux/macOS 验证或设备联调。
