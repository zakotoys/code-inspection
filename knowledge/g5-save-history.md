# G5：通过 MCP 重读、续读与恢复保存批次

更新：2026-09-12。实现、自动验证和用户体验通过；G4 用户已确认测试通过。本文描述当前代码，不将实际 Agent 联调算作已完成。

## 1. 本轮解决什么问题

G4 产生保存观测，但界面只展示最近一份。外部客户端如果过几秒才来查询，不能因为期间又保存过文件，就丢掉之前的观测。

G5 增加有界历史和第三个 MCP 工具 get_save_batches。客户端可按顺序读一页，再从记住的位置继续。读取不会删除数据，两个 Agent 或客户端可以各自读取。

当前完整流程：

```text
VS Code 保存 → G4 等待诊断窗口 → 完成或失效的批次
  → G5 历史追加一条记录，分配 cursor
  → MCP get_save_batches 返回 afterCursor 之后的记录
  → 客户端保存自己的 nextCursor，之后继续读取
```

尚未结束的 pending 观测不进入历史。invalidated 批次进入历史，明确表示这次观测无效；它不能当作没有错误的成功观测。

## 2. batchId、cursor、sessionId 是三件事

| 字段 | 作用 | 何时产生或改变 |
| --- | --- | --- |
| batchId | 标识具体一次保存观测 | 保存开始时产生，完成或失效后不变 |
| cursor | 记录在这一段历史中的顺序 | 批次结束并写入历史时分配，从 1 递增 |
| sessionId | 标识这段历史 | 扩展新实例或工作区文件夹变化时更换 |

cursor 按观测结束顺序，而不是保存开始时间排序。A 先保存但仍在等待，B 后保存却很快失效，B 可以先进入历史。因此不能根据 cursor 推断谁先按了 Ctrl+S。

客户端的 afterCursor 表示“我已经读到这里，请给我之后的记录”，不是数组下标。历史最前面的记录淘汰后，剩余记录的 cursor 不会重新编号。

注意两种会话：G6 已加入暂停/恢复，暂停会清空历史并更换身份，详见 [G6 知识库](g6-lifecycle.md)。get_detector_status 顶层的 sessionId 是 MCP 服务连接身份；get_save_batches 返回的 sessionId，以及状态里的 saveHistory.sessionId，才是历史身份。批次续读必须使用后者。

## 3. MCP 参数和结果

工具：get_save_batches。所有参数都可省略，首次可传 `{}`。

| 参数 | 约束 | 默认 |
| --- | --- | --- |
| sessionId | 历史会话的 UUID；后续读取时携带 | 首次可不提供 |
| afterCursor | 非负安全整数；非零时必须有 sessionId | 0 |
| limit | 每页 1—10 条 | 5 |

例如首次调用：

```json
{ "limit": 2 }
```

成功返回包含 batches、sessionId、nextCursor、hasMore，以及历史容量和边界信息。每条记录的结构是：

```text
{
  cursor: 1,
  payloadOmitted: false,
  batch: { batchId, uri, documentVersion, savedAt, finishedAt, state, ...G4 批次字段 }
}
```

下一次传回上次结果的 sessionId，使用 nextCursor 作为 afterCursor。假设读到了 2，就查询 afterCursor:2。hasMore:true 表示本次读取时还有后续保留记录；hasMore:false 不代表未来不会再产生批次。

没有后续记录时，返回 batches:[]，nextCursor 保持请求的位置。读取不前移任何服务端消费者状态：服务端不知道“Agent A 已处理几条”，这个状态由客户端自己维护。

相同请求在缓存未改变时返回相同结果；旧批次内容不被改写。如果新记录追加到一个原本不足一页的结果后面，再次请求可能多出新记录。如果旧记录已被淘汰，则明确要求重新同步。我们没有提供跨多次请求锁定整个历史的事务快照。

## 4. 为什么缓存不能无限增长

当前限制：

| 层次 | 限制 |
| --- | --- |
| 历史数量 | 最多 100 条 |
| 历史序列化总量 | 最多 2 MiB，按 UTF-8 JSON 字节数计算 |
| 单条历史记录 | 最多 64 KiB；超过则保存摘要 |
| 单页 | 默认 5 条，最多 10 条 |

数量或总量超过上限，从最旧记录开始淘汰。不使用时间 TTL，也不写数据库或磁盘文件。

这些是历史的序列化预算，不是整个扩展进程的内存上限。JavaScript 对象有额外开销，G2 当前诊断和 G4 比较基线也占用内存。MCP 同时提供文本结果和 structuredContent，所以实际网络响应比一份批次 JSON 大；它仍受到单条大小和页数的约束。

若某一条太大，返回 payloadOmitted:true，保留 batchId、保存信息、状态以及诊断/新增/消失数量 counts。诊断数组被省略，而不是伪装成空数组；URI 太长也会截断并标记 uriTruncated。

摘要不能还原原来的完整历史诊断。可以另外查询当前 get_diagnostics 获取当前上下文，但当前状态不等于那次历史保存快照；uriTruncated 的值也不能作为完整文件标识继续查询。

## 5. 过期与重新同步

假设历史保留 6—105，你还停在 cursor 4。查询 afterCursor:4 会漏掉已经淘汰的 5，因此返回 MCP 工具错误：

```text
code: RESYNC_REQUIRED
reason: CURSOR_EXPIRED
oldestAvailableCursor: 6
resumeAfterCursor: 5
latestCursor: 105
sessionId: 当前历史会话
```

服务不会直接给出空列表或悄悄跳过丢失记录。重新同步的步骤是：

1. 把历史缺口记为缺口，不能当作该期间没有错误。
2. 查询当前诊断，重新建立当前上下文；这不能恢复缺失历史。
3. 明确选择从最早保留位置继续，传当前 sessionId 和 resumeAfterCursor。上例会从 6 开始。
4. 若恢复期间又有大量淘汰，可能再次过期，需要再次处理，而不是无限假设成功。

其他错误：SESSION_CHANGED 表示历史会话已更换；CURSOR_AHEAD 表示请求的位置超过当前最新游标。非零游标缺少会话返回 SESSION_REQUIRED。负数、小数、超大 limit、未知参数等会被参数校验拒绝。

第一次使用 `{}`，如果旧历史已经淘汰，也会得到 CURSOR_EXPIRED。这是为了让新客户端知道当前只剩一部分历史。

## 6. 启停、关闭文件与工作区变化

| 操作 | 当前行为 |
| --- | --- |
| 停止/重新启动 MCP 服务 | 历史保留，历史 sessionId 不变；HTTP 地址/令牌按 G3 规则更新 |
| 重载或退出扩展宿主 | 内存历史消失；新实例使用新历史 sessionId |
| 增删工作区文件夹 | 清空历史、更换历史 sessionId，防止继续返回旧工作区记录 |
| 文档对象关闭 | G4 取消该文件等待并清理比较基线；已进入当前工作区历史的记录仍可读取 |
| 重置查看命令的读取位置 | 只改变这个界面客户端的位置，不删除缓存 |

工作区变化采用整体历史重置，避免筛掉部分文件后留下无法解释的游标缺口。仍在范围内的 G4 文件基线继续维护；历史消费端需根据新 sessionId 重新同步。

## 7. 亲自体验：不用终端和剪贴板

1. 停止旧 F5，再重新按 F5。
2. 在开发宿主执行 `Code Inspection: 查看保存观测批次`，然后像 G4 一样完成几次实际保存：干净基线、引入错误、修复。每次等待观测结束再进行下一步。
3. 执行 `Code Inspection: 启动 MCP 服务`。
4. 执行 **`Code Inspection: 通过 MCP 续读保存批次`**。输出显示历史的一页；第一次最多 5 条。
5. 再执行同一命令，它自动携带上次 sessionId 和 nextCursor。读取到末尾后 batches 应为空；这不表示缓存被清空。
6. 执行 **`Code Inspection: 重置保存批次读取位置`**，再续读。应再次读到仍被保留的同一批次，batchId 不变。
7. 再产生一次保存，等待完成后续读，会看到之后的新记录。
8. 停止再启动 MCP，直接执行续读。当前窗口内部会使用新连接信息，历史位置仍可继续；外部客户端需要按 G3 规则更新连接配置。

查询界面只展示本次响应，不自动轮询。如果上一页有 hasMore:true，继续执行命令读下一页。此命令记住的是当前窗口内存中的读取位置，没有消费者数据库。

如出现 RESYNC_REQUIRED，先看当前诊断建立上下文，再执行重置读取位置命令，显式从最早保留历史重新开始。这个按钮不恢复已经淘汰的数据。数据量还少时不必为了手工体验生成上百次保存：自动测试已验证缓存淘汰和错误恢复。

原来的“查看保存观测批次”仍是本地最近观测视图；“通过 MCP 查询当前诊断”仍查询当前快照；现有 mcp:inspect 终端脚本检查状态与当前诊断并列出工具，批次续读使用本轮新命令或直接调用 get_save_batches。

## 8. 为什么读到了 batchId 也不能保证只提醒一次

网络响应丢失时，客户端可能重试同一个游标。服务正确地返回同一 batchId，但如果消费端每读到一次就触发设备，仍可能重复执行。

稳定 ID 只是帮助消费端识别“我见过这次批次”。是否已处理、是否允许重试、如何避免重复动作，需要外部消费逻辑和设备接口共同负责。MCP 只读工具不提供跨程序 exactly-once（恰好执行一次）的保证。

还要区分历史与当前：历史中曾出现过错误，不代表现在仍然存在。invalidated、baseline 或 payloadOmitted 批次也不能直接当作设备动作指令。G5 不运行模型、不触发设备、不实现自动轮询。

## 9. 代码阅读与验证

- src/save-history.ts：追加、序列化限额、淘汰、游标分页和会话重置。不依赖 VS Code 或 MCP。
- src/save-observations.ts：G4 批次结束时写入历史；待定记录尚不入队。
- src/vscode-source.ts：向 MCP 提供历史读取与状态；工作区变化清理旧历史。
- src/mcp.ts：注册 get_save_batches；参数校验，返回结构化结果或明确工具错误。
- src/extension.ts：复用客户端查询代码，维护窗口查看命令自己的游标。
- tests/save-history.test.ts：历史存储的纯测试及 G4 接入测试。
- tests/mcp.test.ts、tests/extension.test.ts：真实协议和真实宿主验证。
