# MCP、Agent 与本项目：从零理解

更新：2026-09-12。本文保留 G1—G3 的概念讲解；G4 保存观测现已实现并通过自动测试，最新行为见 [G4 知识库](g4-save-observations.md)。本文提到的 G3 不保存批次是阶段边界；G5 批次 MCP 续读现已实现，详见 [G5 知识库](g5-save-history.md)；双 Agent 仍未实现。

## 1. 先认识我们正在做什么

你在 VS Code 中写了 `const count: number = "wrong"`。TypeScript 语言服务发现类型不匹配，把错误交给 VS Code；Problems 面板和红色波浪线显示出来。我们的扩展从 VS Code 取出这条诊断，整理成普通对象。外部客户端通过 MCP 查询该对象，Agent 才有机会拿到它并进一步处理。

现在做到的是“诊断能被查询”。“何时查询、是否调用模型、怎么判断是否提醒、如何调用郊狼”还需要外部流程。提供了 MCP 工具，并不表示这些行为已经自动发生。

## 2. 模型、Agent、宿主与工具

| 名称 | 可以怎样理解 | 在本项目中的对应 |
| --- | --- | --- |
| 大语言模型（LLM） | 根据输入生成文字或结构化调用意图的模型 | 将来分析错误的模型 |
| Agent | 用模型、工具和控制流程持续完成任务的程序；具体定义随系统不同 | 将来读取诊断、判断下一步的应用逻辑 |
| 工具（tool） | 有名称、参数和结果的可执行功能 | get_diagnostics |
| MCP Host | 管理 MCP 客户端、上下文及交互的应用 | 可支持 MCP 的 Agent 应用或 VS Code |
| MCP Client | 宿主中负责连接某个服务端的协议组件 | 查询脚本中的 Client 对象 |
| MCP Server | 按协议公开工具等能力的程序 | 扩展中的 LocalMcpService |
| 调度器 | 决定什么时候运行哪一步的普通程序逻辑 | 将来的定时查询或保存批次消费流程 |

模型通常不会自己建立 TCP 连接。它可以输出“调用这个工具，参数是这些”；宿主执行调用，把结果送回模型。是否自动执行、是否需要用户确认，由宿主和应用策略决定。

当前 `mcp:inspect` 脚本只有客户端，没有模型，也没有自主决策循环。这恰好能单独验证 MCP 通信，避免把模型配置错误和协议错误混在一起。

## 3. MCP 到底是什么

MCP 是 Model Context Protocol（模型上下文协议）。可以将其理解为应用与外部能力之间约定好的沟通规则：怎样描述能力、怎样传参数、怎样拿结果、怎样表达错误。

它规范接口，不替你实现业务。我们的业务代码决定“只返回工作区内 Error/Warning”；MCP 负责让客户端以一致的形式发现和调用这项能力。

对比普通函数：`getDiagnostics()` 在同一个程序内直接调用；MCP 调用跨越通信边界，调用方可以是另一个程序，所以需要序列化、传输、参数检查和失败处理。它通常基于 JSON-RPC 消息，但使用 SDK 时不需要手写每一条协议消息。

MCP 也不等于 HTTP。HTTP 是一种承载消息的传输方式；协议还描述工具等能力。当前标准也有 stdio 传输。

## 4. 一次查询实际发生了什么

```text
用户执行“通过 MCP 查询当前诊断”
  → 创建 MCP Client
  → 携带临时令牌连接 127.0.0.1 的服务
  → SDK 完成相应版本的连接与能力处理
  → listTools：发现工具
  → callTool：请求 get_diagnostics，参数 {}
  → 服务检查请求和参数
  → 读取 G2 的当前快照
  → 返回结构化结果
  → 输出面板显示结果
  → 客户端关闭连接（服务继续运行）
```

这里客户端和服务端虽都在扩展宿主进程内，仍然经过真实 HTTP / MCP 路径。外部脚本也能连接同一服务，因此不是用直接读缓存替代协议测试。

不同协议版本的连接流程存在差别，不要直接套用旧教程的固定握手或会话假设。本仓库使用已锁定的 SDK 处理协议细节，业务代码只调用它的公开 API。

## 5. 工具、资源、提示模板有什么区别

MCP 提供的不只有工具。工具用于执行操作、计算或查询；资源用于提供可读取的上下文；提示模板用于提供可复用的交互模板。具体宿主是否支持以及如何呈现，要看其实现。

G3 只注册两个只读工具：get_detector_status 和 get_diagnostics。没有为了“看起来完整”同时加资源和提示模板。只读工具不会因此自动成为绝对安全的内容：返回的错误文字仍来自项目或语言插件，不能当作模型指令。

工具通常包含名称、描述、参数结构和处理函数。参数结构让客户端知道可以传什么，也让服务端拒绝非法参数。我们用 Zod 描述并校验参数；SDK 完成工具注册与协议响应。结果同时提供 JSON 文本和 structuredContent，便于展示和程序处理。

## 6. 为什么选扩展内 HTTP

stdio 使用本地进程的标准输入输出通信，常见方式是宿主启动一个服务进程。Streamable HTTP 使用 HTTP 请求通信，可以部署在本机或远端；用了 HTTP 并不意味着数据会上网。

我们的数据源是 VS Code 扩展 API，已经在扩展宿主中。直接在同一进程提供本机 HTTP，就不需要再启动一个服务进程并建立进程间通信来转发诊断。

| 当前选择 | 理由或代价 |
| --- | --- |
| 只监听 127.0.0.1 | 本机访问，不提供校园网远程访问 |
| 随机端口 | 系统分配可用端口；客户端需要知道当前地址 |
| 每次启动新令牌 | 旧连接配置重启后失效，需要重新复制 |
| 手工启动 | 用户能明确控制何时开放查询 |
| 同进程 | 可复用同一份状态；扩展宿主关闭，服务也关闭 |
| 一窗一服务 | 不同 VS Code 窗口的诊断和连接身份相互独立 |

这种服务只支持当前规定的本地桌面环境。将来如果实际 Agent 只支持其他传输，需要先确认需求再调整，不把尚未验证的客户端当作已兼容。

## 7. 数据是什么，不是什么

诊断是一条带位置的结构化问题，例如下列简化结果：

```json
{
  "severity": "error",
  "message": "Type 'string' is not assignable to type 'number'.",
  "source": "ts",
  "code": 2322,
  "range": {
    "start": { "line": 0, "character": 6 },
    "end": { "line": 0, "character": 11 }
  }
}
```

真实条目还包含文件 URI。位置从 0 开始。扩展并不自己判断 TypeScript 或 Python 语法，而是读取诊断提供方已经发布的结果。没有诊断不等于完整项目没有错误：文件可能没被检查、插件可能没启用、检查可能尚未结束。

当前仓库按文件替换状态。之前有两条错误，下一次该文件只发布一条，就替换为一条；发布空列表就清除。不能永远追加，否则修好的错误还会被反复提醒。

G3 提供的是“现在知道什么”。G4 计划增加“保存这件事发生后观察到什么”。快照与事件历史不是一回事。

## 8. 分页和身份为什么存在

一个项目可能有很多诊断，一次全部返回不利于控制响应大小。因此 get_diagnostics 默认最多 50 条，上限 100 条。

第一步传 `{ "limit": 50 }`。结果给出 sessionId、revision、nextOffset。读取下一页时带上相同筛选条件与第一步的身份。读取之间如果诊断改变，服务返回 RESYNC_REQUIRED，让客户端从头读，避免把旧第一页与新第二页拼在一起。

revision 表示诊断内容版本；sessionId 表示本次服务启动身份。这是应用层身份，不应与协议自身的会话机制混为一谈。observedAt 是最近处理诊断的时间，不能证明所有编译检查已完成。

## 9. 主动查询、被动记录、自动触发

这三个词描述不同位置的行为，可以同时成立。

- 扩展被动记录：VS Code 发出诊断变化事件，扩展更新状态。
- 客户端主动查询：调用 get_diagnostics，询问现在有什么问题。
- 外部流程自动触发：程序按时间或新事件决定是否调用模型，无需人每次输入命令。

当前完成前两项，查询仍由人执行检查命令或客户端代码发起。G3 没有新增保存批次和自动模型调度。

保存触发还要处理时间差：按下保存并不保证语言服务已经给出这次保存对应的全部诊断。后续要讨论观测窗口、连续保存、保存后立即继续编辑和去重，这正是 G4 的任务。

## 10. polling 与 sampling 不一样

Polling（轮询）是调度模式：程序隔一段时间查询一次，有新数据才继续处理。轮询程序不必是模型，用普通 TypeScript 计时器和 MCP 客户端也能实现。是否需要节流、去重和失败重试属于应用设计。

Sampling 在较早的 MCP 规范中表示服务端请求客户端使用其模型生成内容。它不是“每隔几秒查询一次”，也不是两个 Agent 之间天然就能互相唤醒的机制。客户端能力、用户控制和上下文管理都会影响能否使用。

版本提醒：2026-09-12 查阅的官方架构文档明确写明 sampling 自 2026-07-28 协议版本起已弃用；较早的 2025-06-18 规范仍有详细说明，VS Code 的功能页也仍列出相关能力。这些页面对应的版本/实现范围不同，不能把旧教程直接当作当前项目方案。G3 没有实现或依赖 sampling，后续调度需根据项目实际客户端另行确认。

## 11. “两个模型”和“两个 Agent”

“两个模型”描述推理资源，“两个 Agent”描述两个有职责和流程的程序角色。两个 Agent 可以调用同一个模型服务，一个 Agent 也可以按步骤切换模型。

按目前讨论，可以规划为：

```text
扩展：采集确定的诊断
  → 外部调度器：发现新保存批次、去重
  → Agent A：解释和分析诊断
  → 应用策略：决定是否应提醒
  → Agent B / 控制程序：调用既有反馈工具
```

这只是职责建议。语言服务已经能做确定性的类型检查，不需要再让模型重新实现编译器。模型更适合解释问题、理解上下文；但是否需要两次模型调用，要用实际收益、延迟、成本与复杂度判断。MCP 不规定一定要两个 Agent。

提供查询能力、做出提醒决策、执行设备动作是不同职责。当前 code-inspection 只提供诊断，不调用设备、不决定设备参数。

## 12. TypeScript、F5 和两个 VS Code 窗口

TypeScript 为 JavaScript 加入类型检查。编译器把 src 中的 TypeScript 编译到 dist，当前 G7 再用 esbuild 将运行代码和依赖合并为 dist/extension.cjs，扩展宿主运行该 JavaScript bundle。类型检查帮助我们提前发现“工具参数类型写错”等开发错误；它不是替代 VS Code 中用户代码的语言服务。

F5 的 launch.json 使用 extensionHost 调试类型，先运行 compile，再启动另一个带有 extensionDevelopmentPath 的 VS Code 开发宿主。它不是“编译出另一个 VS Code”，而是运行已安装的编辑器，并让该窗口加载本地扩展。

原窗口用于改扩展；开发宿主用于体验扩展。修改源码并不会自动替换已加载的模块，本次修复后应停止旧 F5 调试并重新启动。旧服务的端口和令牌也随宿主关闭而失效。

## 13. 代码阅读顺序

1. src/vscode-source.ts：找出诊断从哪来，什么时候更新。
2. src/store.ts：理解替换、修订号和快照。
3. src/mcp.ts：先看两个工具注册，再看参数检查与 HTTP 入口。
4. src/extension.ts：看启动、停止、复制配置和通过 MCP 查询命令。
5. scripts/inspect-mcp.cjs：从外部客户端视角理解连接与工具调用。
6. tests/mcp.test.ts 和 tests/extension.test.ts：观察预期行为与失败边界。

你不必先背熟 SDK API。先能解释“数据从哪来、谁在什么时候调用谁、失败时显示什么、哪些能力没实现”，再逐步看细节。

## 14. 常见问题：MCP 不就是开一个 HTTP API 吗？

对本项目当前采用的 HTTP 方式，这个理解抓住了“请求数据”的部分。更准确地说，我们提供的是遵守 MCP 规则的 API，HTTP 负责承载通信，Agent 程序中的客户端负责实际发请求。模型通常提出工具调用意图，由程序执行请求并把结果交回模型；模型本身并不是 HTTP 客户端。

HTTP 和 MCP 不是二选一。HTTP 提供请求、响应、方法、状态码等通用通信规则；普通业务 HTTP API 的路径、参数、返回字段可以自行设计。MCP 在业务能力交互层统一了工具发现、工具描述与参数结构、调用及结果等规则。MCP 还可以用 stdio 通信，不一定监听网络端口。

例如自行设计一个接口，可能叫 GET /diagnostics?severity=error，返回 {items:[...]}。这是假设的普通 API，不是仓库现有路由。Agent 开发者需要知道路径、参数和结果含义并编写对应接入代码。

当前 MCP 服务统一通过 /mcp 接收协议请求。客户端调用 listTools 可以发现 get_diagnostics 的名称、用途、参数结构；之后调用 callTool，传入工具名称与 {severity:"error"}，获得结果。/mcp 是 HTTP 路径，get_diagnostics 是 MCP 工具名，两者不是一回事。SDK 包装了实际协议消息，所以代码里的方法调用仍会产生跨通信边界的请求。

| 对比 | 自定义 HTTP API | MCP（使用 HTTP 时） |
| --- | --- | --- |
| 传输 | HTTP | 同样是 HTTP |
| 发现功能与描述参数 | 需另约规则，也可用 OpenAPI 等描述 | MCP 规定工具发现及参数描述方式 |
| 调用 | 按服务各自的路径、方法和字段 | 使用统一协议调用具名工具 |
| 接入多个服务 | 往往需要对应适配；也能借助生成工具减少工作 | 通用 MCP 客户端可复用协议接入逻辑 |
| 业务与授权 | 服务和应用自行实现 | 仍需实现，MCP 不替你做业务或授权决策 |

普通 HTTP API 完全可以给 Agent 用，并非用了 MCP 才能被模型调用。MCP 的价值是共享接入约定，减少不同宿主与工具之间的重复适配；它不会让模型更聪明，也不保证所有客户端自动兼容、自动执行或完全理解业务。

对应当前项目：打开端口是提供可连接的服务；注册工具是声明可以做什么；客户端执行查询是实际调用；接入模型后如何使用结果是再上一层。当前手工查询脚本没有模型，照样可以验证 MCP。
