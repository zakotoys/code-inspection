# G4：保存之后，怎样形成一份可信程度明确的观测

更新：2026-09-12。实现、自动验证和用户体验通过。本文记录 G4 阶段；G5 现已增加历史与 MCP 续读，当前规则见 [G5 知识库](g5-save-history.md)。前置：G1—G3 已实现，用户已反馈 G3 测试通过；项目实际 Agent 联调不在此次验证范围内。

## 1. 本次小目标

G3 回答“现在有哪些已发布的诊断”。G4 回答“这个文件保存后，在限定观测窗口结束时看到了什么，与上次保存观测有何不同”。

新增命令：`Code Inspection: 查看保存观测批次`。命令显示等待中的保存与最近一个已结束批次，并在保存观测变化时刷新。G4 不新增 MCP 工具：get_diagnostics 继续返回当前状态；批次历史、游标和 get_save_batches 属于 G5。

这一步不运行模型，不调用设备，也不把错误数量转换为惩罚规则。

## 2. 为什么按下 Ctrl+S 后不能马上下结论

保存事件表示编辑器完成了一次保存。语言服务可能在保存前已报错，也可能在保存后异步更新，还可能只对某些文件检查。VS Code 的诊断对象没有一项让我们可靠确认“这条诊断属于某次保存的文档版本”。

因此这里使用“保存观测”这个名称。记录保存时的 documentVersion，有助于发现随后编辑使文档变化，但不能证明读到的全部诊断都属于该版本。

示意时间线：

```text
0ms    文件保存，开始等待
300ms  本文件诊断事件到来，重新计算安静期
800ms  之后 500ms 没有本文件诊断事件，完成本次观测
```

如果一直有事件，最长等待的定时目标为保存后 2000ms。到时以 max-wait 原因完成，即使语言服务还没有稳定。JavaScript 定时器受事件循环调度影响，数值不是硬实时承诺，也不是编译完成证明。

## 3. 两个计时器各自负责什么

- 安静期：保存开始时设置 500ms；本文件诊断事件到来就重置，重复但内容相同的事件也会重置。
- 最长等待：保存开始时设置 2000ms，不因诊断事件重置。
- 谁先到就结束观测，同时清理两个计时器。即使保存后没有任何诊断事件，也能结束等待。
- 不同文件各有自己的等待窗口。B 文件的诊断事件不推迟 A 文件。

这可以理解为“等待事件暂时安静，同时给等待设上限”。不是每 500ms 调用一次模型，也不是轮询语言服务。

## 4. 基线、新增和已消失

每个文件第一次成功完成观测时建立基线。假设打开项目时已经有十条错误，第一批会保留这十条 diagnostics，但 baseline:true，added 和 resolved 都为空，不能把已有问题记成十次新错误。

之后与该文件上次成功完成的观测比较：

| 次数 | 观测到的诊断 | added | resolved |
| --- | --- | --- | --- |
| 第一次 | 空 | 空（基线） | 空 |
| 第二次 | A | A | 空 |
| 第三次 | A | 空 | 空 |
| 第四次 | 空 | 空 | A |

added 表示标准化条目此次出现，上次没有；resolved 表示此次不再出现。resolved 不保证用户真正修好了代码，也可能是语言插件撤回了诊断。不要给这些字段添加超出数据证据的含义。

条目比较包含 URI、级别、位置、消息及来源/代码等字段。整体插入一行使位置改变时，可能表现为旧条目消失、新条目出现；这里没有实现跨编辑的语义错误追踪，也不推断作者或责任。错误和警告都保留。

尚未保存时短暂出现错误，然后修复再保存，只看最终观测，不累计中间每个红色波浪线。

## 5. 保存后继续编辑怎么办

最危险的误标是：保存版本 10，然后继续编辑成版本 11，语言服务发布版本 11 的问题，而程序把它写进“版本 10 保存批次”。

当前处理规则：

```text
保存 → pending（等待）
  ├─ 安静期或最长等待到期 → observed（观测完成）
  ├─ 内容继续改变 → invalidated / edited
  ├─ 同文件再次保存 → 旧批次 invalidated / saved-again，新批次开始等待
  └─ 文档关闭或移出工作区 → 取消等待并清理相关基线
```

失效批次的 diagnostics 为 null，表示没有可用观测；它与成功观测的空列表 [] 不一样。失效不会更新基线，下一次成功观测仍与上次成功观测比较。

只把 contentChanges 非空的事件当作内容编辑。VS Code 的 onDidChangeTextDocument 也可能仅报告 dirty 状态改变；保存使 dirty 变为 false 时，不能误判为“用户继续编辑”。

已完成批次不会被随后诊断变化无声改写。即使它记录过错误，也不能证明当前仍有错误；将来的消费端执行动作前需要检查当前状态。

## 6. 返回结构怎么看

顶层包含：

| 字段 | 含义 |
| --- | --- |
| sessionId | 本次诊断采集实例的身份；与 MCP 服务启停身份分开 |
| quietMs / maxWaitMs | 当前窗口参数 500 / 2000 |
| pending | 等待中的保存，包含 batchId、uri、documentVersion、savedAt |
| latest | 最近结束的一份批次；还没有则为 null |

observed 批次额外包含 finishedAt、reason、baseline、diagnostics、added、resolved。invalidated 批次包含 finishedAt、reason、diagnostics:null。

batchId 在保存事件发生时产生，等待到结束保持不变。下一次实际保存事件获得不同 ID；相同诊断再次保存可以有新批次，但 added 为空。

latest 不是“当前正在保存的那个文件”，也不是所有文件的历史。等待新批次期间它仍可能是上一次结果，请看 pending 和 batchId。G4 只保留最近结束批次及各文件比较基线，没有无界历史队列；G5 再增加有界续读。

## 7. 亲自体验

先停止旧 F5，再重新按 F5，确保开发宿主加载新代码。体验不需要启动 MCP，也不需要剪贴板。

1. 在新开发宿主执行 `Code Inspection: 查看保存观测批次`，开始观察输出。
2. 打开 sample.ts，确保是合法的 number 赋值。把数字 1 改为 2 后保存，确保发生实际内容保存；等待约 0.5—2 秒。
3. 应看到 latest.state:observed、baseline:true、added:[]。如果第一次就有问题，也应作为基线保留在 diagnostics 中。
4. 将数字改成字符串 "wrong"，等待 TS2322 出现。尚未保存时，当前诊断会变化，但不会生成新的保存批次。
5. 按 Ctrl+S，等待观测完成。应看到 baseline:false，added 中包含 code:2322。
6. 在文件末尾加一个空行并保存，避免只按 Ctrl+S 而没有实际保存事件。若问题位置、消息等不变，新的批次 added 应为空。
7. 改回合法数字，等待波浪线消失，再保存。应看到 resolved 中包含之前的错误，diagnostics 不再包含它。
8. 体验失效：改一个数字后保存，紧接着继续输入（在约 500ms 内）。若编辑发生在等待阶段，应看到 invalidated、reason:edited、diagnostics:null。若手速没有赶上，可以用下面的自动化测试确定验证该边界。

输出会在批次开始和结束时刷新，但切换到“查看当前诊断”或 MCP 查询命令后显示模式会切换；要继续看批次，再执行保存观测命令。

自动保存也会触发观测；当前按所有 onDidSaveTextDocument 事件处理，不区分手动和自动。为方便逐步体验，可在演示窗口关闭自动保存。保存失败没有完成保存事件，就不会开始批次。

## 8. 代码从哪里读

- src/save-observations.ts：纯 TypeScript 状态机；不依赖 vscode。计时、基线、差集、ID、失效和快照都在这里。
- src/vscode-source.ts：将保存、内容变化、诊断变化、文档关闭和工作区变化接到状态机；继续复用 G2 当前诊断仓库。
- src/extension.ts：新增查看命令和自动刷新的输出视图；MCP 服务启停不控制保存采集。
- tests/save-observations.test.ts：使用 Node 内置可控时钟，精确验证 499ms/500ms、延迟事件和最长等待。
- tests/extension.test.ts：真实 VS Code 中修改、保存、修复 TS2322 并检验批次。

使用内置计时器和现有状态仓库，没有增加运行依赖。只有各文件待定观测拥有计时器，失效/结束/退出都会清理。

## 9. 验证和限制

完整 npm run check 通过：16 个状态/协议测试，其中 7 个是 G4 可控时钟测试；另有空窗口、工作区、重启三个真实宿主场景。工作区与重启场景验证干净基线、保存后的真实 TS2322 新增、保存修复和保存后立即编辑失效。之前 MCP 的真实读取和退出端口清理仍通过。

没有借助用户演示 fixture 做自动化写入；测试使用隔离临时项目。G4 用户体验已确认；实际 Agent、自动保存 UI、多语言保存与跨平台联调没有因此被标为已验证。

范围是激活之后的本地工作区 file 文档。扩展未激活前的保存不回放；文档对象关闭会丢弃该文件比较基线，再次打开后首次成功保存观测重新建立基线。VS Code 的文档关闭事件不等同于每次关闭一个标签页。工作区移除会清理相关记录，重载扩展不恢复历史。

官方 API 依据：本仓库锁定的 @types/vscode/index.d.ts 中 TextDocument.version、onDidSaveTextDocument、onDidChangeTextDocument、onDidCloseTextDocument、languages.getDiagnostics 及 Diagnostic 定义。版本以 package-lock.json 为准。
